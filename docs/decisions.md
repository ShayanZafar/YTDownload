- 2026-10-12 — A source that has refused the app (an HTTP 429 with `Retry-After`) for more than another hour counts as unreliable, however few the attempts. Why: while refused, the app asks it about once per refusal, so a 15-hour refusal from the Spotify Web API never reached the 5 attempts `unreliable` needs, and the session-start hook never prompted the search for another source. (spec `docs/specs/spotify-playlist-past-100.md`, question 2)
- 2026-10-12 — When the rest of a Spotify playlist fails with no `Retry-After` to go by (a 5xx, no connection, a 429 without one), the page asks again by itself a minute later while the panel is open; with a `Retry-After`, at that time. Why: songs past 100 have no other source, and the owner's rule is to wait on our own rather than make someone reopen the playlist. (spec `docs/specs/spotify-playlist-past-100.md`, question 1)
- 2026-10-12 — Delete the stray branch `cursor/paste-link-from-message` (done; its tip was e4418d7). Why: `main` shipped the same Paste feature another way (36a5d07) and has its own ignore rules, so the branch was superseded. (#16)
- 2026-10-18 — Browser tests that use the real YouTube, Spotify or SoundCloud are tagged `@live` and left out of the usual run (`npm run e2e:live` runs them); every other browser test uses stand-ins and runs in CI on every pull request, and a core flow's UI test can't be a `@live` one (`npm run core-flows` checks). A browser download is answered by a stand-in front the page is opened through (`tests/browser/stand-ins.ts`), not by a stand-in yt-dlp. Why: the owner's rule that all three test levels run on every pull request against stand-ins; Playwright's routing doesn't see `<a download>` downloads in Chrome, and a stand-in yt-dlp would need an `.exe` on Windows, where Node can't start a script without a shell.
- 2026-10-25 — No virus scanner of our own (no Defender scans triggered by the app); instead yt-dlp and ffmpeg are checked against their SHA-256 after every install, and folder files against their names by their content (`server/file-kind.ts`). Why: the owner agreed (thread "Add safety checks for downloads"): Windows Defender already scans every file written and every program run, every download is re-made by ffmpeg from decoded or copied audio, and the real risks are the two downloaded programs and files in the folder the app didn't make.
- 2026-10-26 — Fill in details asks MusicBrainz after iTunes and Deezer, uses whichever catalogue has the most of what a song lacks (the earlier on a tie), and marks a song **Not found** only when every catalogue answered and none had it; marked songs are left out of Fill in details unless they're what's listed. Spotify was picked too but is left out: its search answers the anonymous pass 429 for hours. Why: the owner's picks (thread "Sort folder music by genre").
- 2026-10-26 — Renaming a folder song (Sanitize Filename, Rename, Fix name) never adds a number: a name another file has is refused, and Sanitize shows the two songs side by side with a Delete button for each. Why: the owner doesn't want "(1)"/"(2)" names; two songs with one name are usually a copy to delete (thread "Sort folder music by genre").
- 2026-10-26 — Housekeeping lists songs below 128 kbps as low quality by default, with a setting to be stricter (192, 256 kbps, or lossless only, "for truly only high quality folders") or not to check; lossless files always pass, and nothing is deleted until the person ticks it and confirms (to the Recycle Bin). Why: the owner's pick and follow-up (thread "Sort folder music by genre"); 128 kbps is audibly poor below, and most YouTube audio is 128–160 kbps.
